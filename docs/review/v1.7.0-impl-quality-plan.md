Prepared offline. No agent or model was run. Everything that needs an app *generated by a model from a
brief* is **E0B/E1 NOT_RUN**; this increment built the contracts, the validator, the adversarial tests
and a verified negative control, and validated them against the existing reference apps (standing in for

## What exists vs what a future run adds

- **Now (E0A/E0B over the reference apps):** the five `scenario.json` contracts, the contract validator,
  the axis-aggregation rules, the adversarial integrity tests, and the a11y negative control. The
  reference apps and their `check-*.mjs` already exercise the four axes' automatable parts in the gate.
- **A future run (E0B/E1, NOT_RUN):** give each scenario's **brief** to a model (with / without
  Frontend Architect), let it BUILD the app, then run the same contract axes on the generated artifact.
  That is the behavioural measurement; it needs a model, authorization and a budget.

## Human visual review strategy (axis D, E2)

The visual axis never auto-passes. The mechanical part (token consistency via `design-consistency`,
reduced-motion honored, the five data-view states present) is E0A. The judgement — hierarchy,
composition, density, identity, motion taste — is **HUMAN_REVIEW_REQUIRED** and produced as evidence,
not a verdict:
- Reuse the existing capture pipeline (`verification/browser/review-captures.mjs` + `gallery.mjs`) to
  render each built artifact across viewports and themes into a contact sheet.
- A person grades against the scenario's `human_review.rubric` (e.g. "does the hero read in one glance",
  "is density right for long shifts"). The grade is recorded as a human E2 verdict; only then can the
  scenario reach an unqualified PASS.
- A clean axe run, a passing Lighthouse, or a matching snapshot is **never** a visual PASS — the
  validator and the tests enforce this structurally.

## Version-comparison strategy (prepared, NOT run)

To ask "does Frontend Architect help build better frontends", run the SAME briefs under three arms, the
same model/params/tools/time/budget, changing only the skill:
1. **No Frontend Architect** — the model with no plugin.
2. **Frontend Architect v1.6.0** — the published skill.
3. **Frontend Architect v1.7.0** — the candidate.

Each arm builds each scenario; the four contract axes score each built artifact (A/B/C automated, D
human). Report per-arm, per-scenario, per-axis — never a single merged "quality score". Controls:
- pin the agent model id and params, the allowed tools, the max turns, and a `--max-cost-usd` ceiling;
- run each arm the same number of times; one run proves nothing — do not claim causality from a single
  build (frontend generation is high-variance). A credible signal needs several runs per arm and the
  variance reported alongside the means.
- the arms differ only in the skill; the brief, the grader and the environment are identical.
This is E0B (build) + E1 (any model-judge) + E2 (human visual). All **NOT_RUN** until authorized.

## Cost estimate (future, authorized separately)

Building an app from a brief is heavier than answering one. Using the measured range in `docs/evals.md`
(an audit answer ~0.28 USD/run at 10 turns; longer build tasks run more turns and tokens):
- a build run is plausibly **1–3 USD** at a mid model, more at the strong model, per scenario per arm.
- 5 scenarios × 3 arms × 3 runs ≈ **45 build runs** → a working range of **~45–135 USD** at a mid model,
  bounded hard by `--max-cost-usd`; cheaper on Haiku, several times more on the strong model.
- the automated axes (A/B/C) add only the gate's own compute (free); the E1 judge, if used for code
  quality, adds judge tokens; the E2 human review is human time, not model cost.
- **Nothing runs without an explicit budget and your authorization**; a first pilot would be one
  scenario, two arms (no-FA vs v1.7.0), one run, Haiku, under a 10 USD ceiling.

## Honest limits

- The reference apps stand in for "a correct build"; they are not model-generated, so the automated axes
  are validated, but the end-to-end "does the skill help" claim is NOT measured here (NOT_RUN).
- The negative controls prove the axes can FAIL on known defects; they are minimal, not a census of
  every defect class.
- Visual quality is irreducibly human; the system surfaces evidence and refuses to fake a verdict.
- A single build run is not evidence of causality; the comparison needs repetition and variance.
