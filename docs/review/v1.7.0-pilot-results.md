# Behavioural pilot — first real runs (E0B, exploratory)

Dates: 2026-11-10 and 2026-11-13. Provider: the operator's personal claude.ai subscription (`EVAL_PROVIDER=claude-ai`,
first-party login, org pinned). Judge: `haiku` throughout. Tree: the published 1.7.0 plus the local harness fixes
listed below (SHA recorded per run in the scratch logs). **One case, one run per arm per configuration — exploratory
data, not a measurement of the skill.** Nothing here certifies v1.7.0. Estimated cost as reported by the CLI:
**≈ 0.57 USD across the first eight launches (six costed, two aborted at 0 cost)** (plan usage, not an invoice).

## What the first launches found before any valid run happened

The first two launches ran **no case** (cost 0) and the third was invalid as a measurement. Each exposed a defect in
the 1.7 evaluation harness or cases that offline validation could not see — the reason the pilot exists:

| # | Symptom | Root cause (verified) | Fix |
|---|---|---|---|
| 1 | CLI refused to start: `"MultiEdit" cannot be disallowed … No case was run` | `MultiEdit` is not a built-in tool of CLI 2.1.x | removed from `--disallow-tools`; test |
| 2 | `No eval cases found matching --case "96-*"` | `--case` filters by the case's `name:`; the directory is `96-arch-positive`, the name `arch-positive` | `CASE=<dir glob>` translates to the name; test |
| 3 | plugin arm: Bash denied, 3 turns, judge FAIL; `result.json` showed `maxTurns 10, timeout 300` | the 21 tool-using cases declared `allowed_tools`, `max_turns`, `timeout_seconds` at the **top level** of `case.yaml`; schema 1.1 reads them under `execution:` and ignored them silently (no validator objects) → defaults, **no Bash** | moved under `execution:` in all 21; `eval-case-schema.test.mjs` pins it |
| 4 | traces gone after the run | temp scaffold dirs deleted by the CLI | `--keep-temp` + copy `trace.jsonl` to `results/<run>/traces/`, then remove the sealed dirs tolerantly |
| 5 | with the schema fixed, Bash still denied on `Bash(node:*)` and on a read-only allowlist | agents invoke scripts as `cd …; S=<plugin>/scripts; node $S/domain-deps.mjs …`; a prefix rule must match **every** subcommand and never matches an expanded variable; after one denial the models concluded Bash was unavailable | **full `Bash`** in audit/pilot (Write/Edit/WebFetch/WebSearch still removed), stated as not a sandbox |
| 6 | `skill-activation = no` although Sonnet had delegated to the plugin's `frontend-reviewer` | the indicator counted only the `Skill` tool | `subagent-activation` indicator (`Agent` with `frontend-architect:*`) on every tool-using case; `summarize.mjs` shows both |

## What can honestly be said

1. **The machinery works end to end** under the personal provider: provider guard, budget guard, scaffold, both
   arms, graders, traces, cost. The acceptance items of the plan that concern the machinery are met for this case.
2. **Activation happens, by two routes.** Haiku invoked the `Skill`; Haiku (full Bash) and Sonnet delegated to the
   plugin's `frontend-reviewer` subagent — the route SKILL.md prescribes for a broad audit. An indicator that counts
   only `Skill` under-reports activation; both are now reported.
3. **With Bash available, the plugin arm runs the auditors and they find the planted defect.** Without it, every
   model fell back to reading files after one denial and never retried — a property of the models and of the CLI's
   denial message, not of the skill.
4. **Case 96 does not discriminate.** The no-plugin arm found `useOrders.ts:1` by reading 12 files in every valid
   run; Δ = 0 in both full-Bash runs. A planted defect that `grep` finds cannot show the value of a dependency graph.
   The cases that need tooling to answer (bundle attribution over a build, hydration cost, route guards across
   files, perf budgets) are where a difference could appear — or not.
5. **Nothing statistical.** One run per configuration; judge votes split 2/3 on several runs; model variance is
   visible run to run (3–21 turns for the same prompt). No claim that Frontend Architect makes Claude Code better
   follows from this, and none is made.

**The plugin was loaded in every plugin arm (the init event lists both skills and the `frontend-reviewer` agent) and
Bash was never denied — and Haiku activated neither the `Skill` nor the subagent in 0 of 8 cases**, against 2
activations in the 3 earlier single-case runs with the same model. Where the plugin arm "won" (perf, abstain-single)
it did so without the skill: model variance, not the plugin. Where the judge encodes the skill's doctrine (routes,
a11y, bundle) both arms fail, because the arm that could have applied the doctrine never loaded it.

Seventh defect, found by this run: the bundle scaffolds resolved the repository root with `git rev-parse` first, and
`claude plugin eval` initialises a git repo in the sandbox home, so the fixture path resolved inside the sandbox.
Fixed (own-path first), regression test, re-run verified.

### Reading for the roadmap
- **Activation is the bottleneck, for both models.** Haiku 2/11, Sonnet 3/10 across every run: the plugin is loaded, Bash
  is available, the prompts carry the trigger phrases, and the model mostly answers on its own. The skill description
  and triggering deserve their own evaluation (`v1.8.0-activation.md`: a before/after of the proposed wording on these
  eight cases) before any further spend on diagnosis quality.
- **Cases that reading alone can answer (96, 99) will never show a difference**; the discriminating cases are the
  ones that need the tool or the doctrine (routes framing, a11y completeness, bundle over a build, perf budgets).
- **Judge criteria encode doctrine on purpose** — that is what makes the no-plugin arm fail — so "both fail" on a
  doctrine case means "the skill was not applied", not "the case is broken".
