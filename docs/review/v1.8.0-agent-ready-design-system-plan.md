# v1.8.0 design — an agent-ready design system for Vue/Nuxt (planning only)

Status: **APPROVED 2026-11-13 ("continúa con todo"); increment 1 done, see §8.** Written 2026-11-10 after reading `meta/astryx`
(README and `packages/cli/README.md` through the GitHub API, nothing cloned). v1.8.0 does not start until the 1.7
line is closed (5B pushed and CI green; the behavioural pilot run or explicitly deferred).

## 1. What Astryx is, and what in it is worth replicating

Astryx (`meta/astryx`, MIT, React 19 + StyleX, beta, 22k stars on 2026-11-10) is Meta's internal design system
released as open source: 150+ components, themes, templates and a CLI. Its stated difference is not the
component count but the **model**: people and agents build from the same reference.

| Astryx piece | Mechanism | Worth replicating for Vue? |
|---|---|---|
| 150+ components, charts, richtext, native | a library with an eight-year team behind it | **No.** Nuxt UI, Reka UI, PrimeVue and shadcn-vue already exist and are maintained; a skill must orchestrate them, not compete |
| `astryx component [--list|<Name>]`, `hook`, `docs <topic>`, `search` | the CLI answers "what exists, how is it used" with `--json`, `--detail brief|compact|full`, `--dense` (token-efficient text) | **Yes** — as a read-only inventory of the *project's own* design system, in the skill's audit-script form |
| `astryx manifest --json` | capability discovery for agents: every command, option and response type | **Yes**, in miniature: the inventory's `--json` contract and an emitted `AGENTS.md` section |
| Theme = CSS custom property overrides, `theme add|switch|build` | no forking, no wrapping | **Already have it:** `design-contract.mjs --emit css|tailwind|nuxt-ui|dtcg`. Missing: theme *packages* (neutral + brand) as a generated artefact and the multi-brand switch |
| Open internals + `swizzle` (eject a component's source), `upgrade` refreshes copied components | own the source when you need to go deeper | **Yes as doctrine** (eject vs wrap decision; shadcn-vue is the Vue precedent) and as a *detector* (the inventory knows which components are ejected copies and whether they drifted); **no** as a tool that copies code |
| `template`, `build` (page templates and a workflow playbook) | ready-to-ship pages | **Partly:** the five reference apps are already templates; a small design-system starter is the missing one |
| `doctor`, `gap-report`, `integration`, `blog`, `discover` | ecosystem/governance tooling | No (out of scope for a skill) |

## 2. Vue ecosystem mapping (to re-verify on npm at implementation time)

- **Nuxt UI** (v4 line: Reka UI + Tailwind v4, `app.config` theming, `ui` prop per component, an official MCP
  server) → the `@astryxdesign/core` role for Nuxt apps. The design contract already emits its `--ui-*` mapping.
- **Reka UI** (headless, the base of Nuxt UI and shadcn-vue) → "open internals": composable primitives.
- **shadcn-vue** (components copied into the project from a registry) → the swizzle model; components are
  project-owned source by construction.
- **PrimeVue** (styled + unstyled/pass-through modes) → the alternative when a team standard requires it.

The skill does not pick one; `component-libraries.md` already frames the choice. The new work makes the chosen
library's design system *legible to agents* and *auditable*.

## 3. Deliverables

### A. `scripts/design-system-inventory.mjs` — the `component --list` / `docs` of the project's own system
Read-only, dependency-free, same conventions as the fifteen scripts (`<project-root> [--json|--md]`, `confirmed |
heuristic | info`, exit 0/1/2, `Analysis` line naming the engine, `.frontend-audit.json` keys). Reuses
`lib/source.mjs` (`parseSfc`, `templateTags`, `extractImports`, `extractExports`) and the semantic engine when
the project's TypeScript and `vue/compiler-sfc` are installed; lexical fallback otherwise.

Answers, per component found under the design-system roots (`components/ui`, `components/design-system`, a
configured list; Nuxt layers respected):
- identity: name, file, owner (`project` | `ejected-copy` of library X | `library-wrapper` around X | `library`),
- API: props (runtime and type-based `defineProps`, with defaults), emits, slots (named/scoped), exposed, `v-model`s,
- variants: `ui` prop / `app.config` overrides (Nuxt UI), `cva`/`tailwind-variants` definitions, data-attribute states,
- tokens: which CSS custom properties / Tailwind theme tokens it consumes; literals that bypass the token layer (delegated to `design-consistency.mjs`, not duplicated),
- states: whether a data-view component declares loading/empty/error/partial/success (the five-states rule),
- a11y surface: `aria-*`, label props, keyboard handlers present (static only; `ui-audit.mjs` grades them),
- documentation: has a docblock / story / usage example or not,
- drift: for an ejected copy, whether the registry marker and the local source still agree (hash or version comment).

Outputs: `--json` (contract below), `--md` (a dense table for people), **`--agents`** (a Markdown section meant to
be pasted or linked from `AGENTS.md`/`CLAUDE.md`: the component list with one-line API summaries, the token roles,
the rules — the Vue equivalent of `astryx docs --dense`). Findings (confirmed/heuristic) only for defects:
undocumented public component, component without the five states, ejected copy that drifted, wrapper that
re-exports a library component unchanged (pass-through layer), token bypass count above the policy.

JSON contract (v1): `{ tool, version, analysis, root, library: {name, version|null, source}, components: [...],
tokens: {roles: [...], unused: [...]}, findings: [...], summary }` — frozen with a contract test like 1.2.0–1.4.0.

Honesty bounds: static; never renders; runtime-computed variants and props spread from objects are `heuristic`;
no claim about visual correctness (that is `browser-audit`/E2); a library's internals are not inventoried, only
the project's use of them.

### B. `references/agent-ready-design-system.md`
Doctrine, one page: one reference for people and agents; open internals; the eject-vs-wrap decision (eject when
you need the internals or the library's API blocks a requirement; wrap only to fix a project convention; never a
pass-through); theme = contract-emitted CSS variables, brands as override files, tenant switch without a rebuild;
how to expose the system to agents (`design-system-inventory --agents` into `AGENTS.md`, the Nuxt UI MCP when
present, the contract JSON as the token source of truth); governance (what changes need a contract change, an
inventory diff in review). Row added to the SKILL.md table; `index.md` and `capabilities.md` updated.

### C. `assets/design-system-starter/` — a Vue/Nuxt starter of the model
Not a library: a contract (`design-contract.json`), two theme files emitted from it (neutral + one brand), 8–10
seed components on Nuxt UI/Reka following the doctrine (at least one ejected copy with its marker, one data view
with the five states, one form control, one dialog), the inventory wired in `package.json`, and an `AGENTS.md`
produced by `--agents`. Verified like the reference apps: extracted and built in the gate, `browser-audit` 0
confirmed, inventory output pinned as a frozen truth.

### D. Evidence
- E0A: unit tests with fixtures and hand-written ground truth for the inventory (props/slots/variants/owner/drift),
  contract test, byte-identical-project test, exclusion and policy tests.
- Corpus: 8–12 adversarial cases in `verification/corpus` with `truth.json` (FP traps: a wrapper that *does* add
  behaviour; props spread from a typed object; a Nuxt layer component; FN misses: `defineProps` from an imported
  type, a variant table in a separate file), measured with `measure.mjs`, reported with the dev/hold-out split.
- Reference apps as ground truth: Atlas (Nuxt UI and shadcn) and Ember inventories pinned.
- Eval cases: three tool-using cases (positive, clean, abstain) in the E0B form of 1.7; **NOT_RUN** until authorized.

## 4. Out of scope (said plainly)
A component library; Storybook/Histoire; Figma or token sync; React (Astryx itself covers it); any tool that
writes into the user's project (the skill's scripts stay read-only; the starter is an asset, copied by the user).

## 5. Increments (each stops for human review, gate green, local thematic commit)
1. Design freeze: JSON contract v1 + fixture set + truth (no script yet).
2. Inventory core: discovery, owner, props/emits/slots, `--json`/`--md`, tests + contract test.
3. Variants, tokens, states, drift; `--agents`; findings and policy; corpus cases + measurement.
4. Reference + SKILL.md/index/capabilities rows; frontend-reviewer runs the inventory in audits.
5. Starter asset, built and verified in the gate; inventories of the reference apps pinned.
6. Eval cases (NOT_RUN), docs, CHANGELOG, metadata 1.8.0, independent fresh-context audit, privacy sweep.

Acceptance for the line: inventory precision/recall on the dev corpus ≥ the 1.7 bar (96/94) with the hold-out
reported separately; gate exit 0; plugin-check 0 warnings; no production rule of the fifteen scripts changed.

## 6. Risks
- Scope creep toward "a library": the starter must stay ≤ 10 components; the doctrine does the rest.
- Nuxt UI v4 API churn: pin the version in the starter; the inventory reads the project's installed version.
- Type-based props need the project's TypeScript; the lexical fallback will under-report (heuristic, stated).
- `--agents` output drifting from the code: it is generated, never hand-edited; a test diffs it against the inventory.

## 7. Decisions (taken 2026-11-13 with the recommended options)
1. Roots: `components/ui`, `components/design-system` (and under `app/`), plus the same paths in every Nuxt layer the
   config extends — layers included by default, each component carries its `layer`; override via `.frontend-audit.json`.
2. `--agents` prints to stdout only, like every other script.
3. Starter on Nuxt UI only in 1.8.
4. `frontend-reviewer` runs the inventory in its default sweep when a root exists.

## 7b. What the behavioural pilot added to this plan (2026-11-13)
The first real runs (`v1.7.0-pilot-results.md`) showed that **activation is the bottleneck**: with the plugin loaded
and Bash available, Haiku activated the skill in 0 of 8 cases in one run and in 2 of 3 in others; Sonnet activated
(via `frontend-reviewer`) in both of its runs. An agent-ready design system that the agent never consults is worth
nothing, so 1.8 gets an extra, early increment — **1b: activation** — that (a) reads the two skill descriptions and
the reviewer agent's description against Claude Code's documented triggering rules, (b) adds E0A checks on their
length/specificity, and (c) proposes wording changes to be evaluated with the pilot's eight cases on Sonnet before
and after (one run per arm; exploratory). No description change ships without that before/after.
