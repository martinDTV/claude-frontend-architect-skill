# Hold-out validation set — design (1.7 increment 3B)

The increment-3 corpus is a **development set**: it was authored and measured in one pass, so its 96.4 %
precision / 94.6 % recall are in-sample numbers. A hold-out set exists to answer a different question:
do the tools generalize to cases that were **not** available while the corpus (and, in a future
increment, any rule fix) was written? This document DESIGNS that set. It is not built here — building it
needs explicit authorization (Fase 3 says stop before creating it if it requires new tooling or changes;
it does not, but the standing restriction is "no commits without later authorization"). Nothing below is
executed.

## Purpose and the one rule that makes it a hold-out

A hold-out is only valid while it stays **unseen by the thing it measures**. The thing it measures is the
auditors (`domain-deps`, `state-audit`, `routes-audit`, `perf-audit`, `ui-audit`, `route-attribution`).
So the governing rule is:

> **The hold-out's results may never be used to change an auditor's rules, nor to edit the development
> corpus.** If a hold-out case reveals a tool defect, that defect is reported; any fix is driven by the
> defect itself and re-validated on the development set, and the hold-out case that exposed it is then
> **retired** (moved into development) and replaced, because once a fix targets it, it is no longer unseen.

## What "not a trivial copy" means (anti-leakage)

Each hold-out case must differ from every development case in a way that exercises the SAME rule through
a DIFFERENT surface, so passing it is evidence of generalization, not memorization:
- different framework where the rule is framework-agnostic (a Nuxt case where development used Next, etc.);
- different library/identifier names (not the same `useApi`/`SceneHero`/`billing` the dev set used);
- a different syntactic carrier of the same defect (e.g. a dynamic `import()` with a template literal vs
  a static namespace import; a guard via a route-group layout vs middleware);
- a different file/line layout so line-matching cannot succeed by coincidence.
Two reviewers' rule of thumb: if a diff against the nearest development case is only renamed symbols, it
is a trivial copy and must be rewritten.

## Size and stratification (proposed)

Smaller than the development set (a hold-out is a check, not a second corpus): **~18 cases**, 3 per area,
drawn from the categories where generalization is most in doubt — deliberately weighted toward the edges,
not the easy positives:
- 1 **real-defect** per area, in a new framework/surface.
- 1 **correct-suspicious OR negative-control** per area (precision under new-looking-but-clean code).
- 1 **the area's known weak spot** per area, to see whether the limit reproduces on unseen code:
  - arch: a symbol laundered through a *third* module's public index (the semantic-engine blind spot).
  - state: the variable-resolution miss in a different shape (`const k='refresh'; store.set(k, token)`).
  - routes: auth via a *differently named* helper than `ensureLoggedIn` (does the FP reproduce?).
  - perf: a heavy module via a bare side-effect `import 'heavy/styles'` (does the re-export/side-effect FN reproduce?).
  - a11y: a different custom ARIA widget (`role="combobox"`) with no name (the out-of-scope gap).
  - bundle: a heavy chunk just over threshold on a *different* route shape.

## Ground-truth rule (identical to development, stated again)

Each hold-out `ground-truth.json` is written **from the source by hand, before running any tool**, same
schema as `verification/corpus/README.md`. The author of a hold-out case must NOT look at the tool's
output while writing its truth.

## Execution and reporting (when authorized)

- Store under `verification/corpus-holdout/<area>/` (a sibling tree, so `measure.mjs --root` can target it
  separately and it never mixes into the development aggregate).
- `measure.mjs` would need one additive flag (a root override) — a measurer change, not an auditor change;
  propose it separately and keep it out of any auditor commit.
- Report development and hold-out numbers **side by side, never merged**: a gap (hold-out recall < dev
  recall) is the generalization signal.
- A hold-out run is still E0A (tools vs fixtures, deterministic, no model); it is NOT E0B/E1.

## Why this is not built in 3B

Fase 3 asks to DESIGN the hold-out and to STOP before building it if building needs new tooling,
public-contract changes, or models. Building it needs none of those, but the increment's standing rule is
"no commits without later authorization for concrete corrections." So this is the design; construction is
a separate, authorized step. If authorized, it is ~18 fresh cases plus the one additive `--root` flag on
the measurer, with the anti-leakage and no-rule-tuning rules above enforced.
