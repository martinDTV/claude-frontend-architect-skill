# v1.5.0 — Controlled evaluation proposal for the UI briefs 85–88 (increment 6, pre-publication)

Nothing in this document runs an evaluation. It is a methodology review and a budgeted plan for your authorisation. No paid run, no publication, no install, no scaffold. HEAD stays `8bcc71e`.

## 0. What these evaluations actually measure, and what they do not

The four cases (85 logistics admin, 86 premium landing, 87 specialty store, 88 redesign of an inconsistent UI) give an agent a written brief with **no repository in the session** and grade the plan it writes. So the unit under test is:

> the quality and shape of an agent's **written frontend plan** from a brief, and whether the `frontend-architect` skill **fired**.

That is a fair proxy for what the skill adds to planning and decision-making. It is **not** a measure of production code quality, of whether the three reference apps are good (the visual review and the browser checks cover that), or of WCAG conformance. Read a pass as "the plan follows the method the skill teaches", not "the skill makes better software". This framing matters for point 13 below.

## 1–13. The methodology, point by point

| # | Item | Answer for this suite |
|---|---|---|
| 1 | Model and version actually used | The **agent** model is whatever you pass to `--model`; the realistic target is `sonnet` (the deployment's current Sonnet alias) because these briefs ask for long structured plans a Haiku answer tends to under-cover (observed in the smoke run: case 48 failed on Haiku for exactly that). The **judge** is `--judge-model haiku`. Both resolve against your Vertex deployment; pinned ids such as `claude-haiku-5-5` may not be enabled, so the aliases are safer. The exact resolved ids are written into each run's `result.json` and must be read back, not assumed |
| 2 | Runs per case | `--runs 3` for the pilot (one run is noise, as the smoke run showed opposite PASS/FAIL on re-runs of the same case). The suite default is 3 |
| 3 | Cost per run | From the 2026-10-28 runs: a Sonnet audit case cost 0.28 USD at 10 turns; these briefs load the ~16 KB skill plus several references and answer at length, so **0.4–1.0 USD per with-plugin run**, the baseline arm cheaper; **~0.06 USD per run with Haiku** |
| 4 | Total cost and ceiling | Pilot (2 cases × 3 runs × 2 arms = 12 runs): **~6–8 USD with Sonnet**, ~1 USD with Haiku; propose `--max-cost-usd 10`. Full suite (4 × 3 × 2 = 24 runs): **10–25 USD with Sonnet**, 2–5 with Haiku; `--max-cost-usd 30`. The ceiling aborts with partial results if the range is wrong; with `-j 2` the overrun is bounded to the runs in flight |
| 5 | Token consumption | Each run reads the skill body (~4 k tokens) plus the references it opens (design-contract, enterprise-application, forms, accessibility, ui-verification: roughly 8–15 k tokens) and writes a long plan (2–5 k tokens). Call it **~15–25 k input + ~3–5 k output per with-plugin run**; the baseline arm reads no skill, so a few k less. 24 runs ≈ 0.5–0.7 M tokens total. These are estimates, not measurements; the real figures land in `result.json` cost/token fields |
| 6 | Tools needed | `Read, Glob, Grep, Skill` are always granted. `Bash` is operator-gated by `--allow-tools Bash`; with it the agent may run `capabilities.mjs` or `design-contract.mjs` inside its sandbox, which cases 86/88 can use. Without it the cases still answer from the references. No MCP servers, no scaffold scripts for 85–88 |
| 7 | `--no-publish` | **Always set.** Without it the HTML report is published to claude.ai. The run script `verification/evals/run-evals.sh` hard-codes `--no-publish`; the proposed commands below keep it |
| 8 | Isolation in temporary directories | The agent runs inside the CLI's OS sandbox with a clean working directory (the briefs confirm "no repository in this session"). Scaffold dirs, when used, are temp dirs; 85–88 use none. Results go to `plugins/frontend-architect/evals/results/<mode>-<stamp>/`, which is gitignored. `--keep-temp` can preserve the sandbox for inspection |
| 9 | Bash restrictions and side effects | `Bash` runs **as you, outside the OS sandbox's network limits for mock/scaffold graders**, per the CLI's own warning; for 85–88 there are no mocks or scaffolds, so Bash would only let the agent run the plugin's read-only scripts. If you prefer zero Bash, pass `--disallow-tools Bash` (the cases still pass from the references) — see the leakage mitigation in §3 |
| 10 | Scoring rubric | Each case has `graders/criteria.md` (`type: llm`, weight 1): an explicit PASS/FAIL list the judge model applies (contract before screens, stage-1 architecture with exclusions, named behaviours, accessibility and 200%-text reflow, a verification plan separating proved/flagged/judged, proportionality, references named; and a FAIL list for starting from colour, a global store for server data, missing states, claiming quality without measurement). A PASS requires a majority of judge votes across runs |
| 11 | Approval criteria | Per case, PASS = the judge's majority verdict on `criteria.md`. For the **suite**, I propose: adopt no claim of "the skill helps" unless the with-plugin arm passes a case the baseline arm fails, **and** that gap holds across the 3 runs (not a single flip). Activation (the `skill-activation` indicator, `arm: with-only`) must be ≥ 1 in the with arm; it is excluded from the baseline and from the score |
| 12 | Reproduction procedure | `./verification/evals/run-evals.sh tag suite:ui-briefs` with `MODEL`, `RUNS`, `BUDGET` set, or the explicit command in §4. There is **no seed or temperature flag** in `claude plugin eval`, so exact reproduction is not possible; reproduce the *distribution* by re-running with the same N and reading the spread, not a single number |
| 13 | Separating model / skill / judge / environment failures | Four controls: (a) **skill vs model** — the `with-without` ablation runs the same brief, model and tools with and without the plugin; the delta isolates the skill. (b) **judge** — a FAIL whose `criteria` reasoning misreads the answer is a judge failure, not a skill failure; spot-check the judge transcript on any surprising verdict, and a second judge model can be run on the same answers. (c) **environment** — `result.json` carries `error` fields (the 2026-10-28 runs scored 0 purely from Vertex credentials and a disabled model id); `summarize.mjs` prints an `errors` column so these are not read as answer failures. (d) **variance** — the smoke run flipped PASS/FAIL between two runs of one case, so a single run separates nothing; N ≥ 3 and the spread do |

## 2. The controlled comparison (A vs B)

This is a built-in mode, not something to hand-build.

- **Arm A (with):** Claude Code + `frontend-architect` 1.5.0, the given model, the given tools, the brief.
- **Arm B (baseline):** the same model, the same tools, the same brief, **no plugin loaded**.

`--ablation with-without` (the default when a plugin resolves) runs both arms and reports the per-case score delta. Everything that must be constant is constant by construction: same prompt, same model id, same tool grants, same judge, same run count. The only difference between arms is the presence of the skill. The `skill-activation.md` grader is marked `arm: with-only`, so it records activation in A and is excluded from B and from the score — it answers "did the skill load", not "is the answer good".

What the delta can and cannot say: a positive delta that holds across 3 runs is evidence the skill shapes the plan; a delta of one flip is within the observed run-to-run noise and says nothing. Do not read a small delta as an improvement.

## 3. Leakage: can the agent see the answers?

The risk you named: the agent must not reach `graders/criteria.md`, the `expected_outcome` frontmatter, or prior `results/`.

- **By design,** the briefs run with no repository in the session and the sandbox gives a clean working directory; the plugin is loaded for its *skills*, not as a readable tree of its `evals/` folder. The capability cases already rely on this ("inside the eval sandbox no external skill exists").
- **This must be verified, not assumed.** Before any scored run, do a leak check: run the pilot once with `--keep-temp` and `--disallow-tools Bash`, then inspect the preserved sandbox working directory — confirm it contains no `graders/`, no `expected_outcome`, no `results/`. If `Bash` is granted, also confirm from the transcript that the agent did not `grep`/`cat` its way to those files. If the sandbox does expose them, the mitigation is `--disallow-tools Bash` (the cases pass from the references) and, if needed, running the eval from a copy of the plugin with `evals/graders` and `evals/results` removed.
- **Judge leakage** is separate and expected: the judge *is* given `criteria.md` — that is its rubric, not the agent's. The agent never sees the judge's input.

## 4. Proposed pilot (low cost, not executed)

Two contrasting cases: **85** (enterprise SaaS) and **86** (premium landing), which exercise the two halves of the skill (architecture-first vs motion-and-identity). Minimum runs for a signal over noise: 3 per case per arm.

```
# PILOT — for your authorisation; do not run until the budget is approved.
./verification/evals/run-evals.sh tag suite:ui-briefs   # then narrow, or the explicit form:

claude plugin eval plugins/frontend-architect \
  --case '8[56]-*' --ablation with-without \
  --model sonnet --judge-model haiku \
  --runs 3 -j 2 \
  --allow-tools Bash \
  --no-publish --trust-plugin \
  --max-cost-usd 10 \
  --output-dir plugins/frontend-architect/evals/results/pilot-ui \
  --json plugins/frontend-architect/evals/results/pilot-ui/result.json \
  --report plugins/frontend-architect/evals/results/pilot-ui/report.html
# leak check first (one run, no Bash, keep the sandbox to inspect):
#   ... --runs 1 --disallow-tools Bash --keep-temp
```

| Pilot parameter | Value |

| Arms | with + baseline (`--ablation with-without`) |

## 5. Security and operating constraints (mapped to the command)

| Your constraint | How it is met |
|---|---|
| No arbitrary commands from the briefs | 85–88 define no scaffold; `--no-scaffold` is implied by not passing `--scaffold`. The only tool that runs anything is `Bash`, which runs the plugin's own read-only scripts, or is denied with `--disallow-tools Bash` |
| No installing dependencies or global plugins | The eval loads the local plugin; it installs nothing. No `npm i`, no plugin install |
| No credentials, personal profiles, other repos | The sandbox has a clean working dir and no repository; the capability cases pass only because no external skill or profile is present |
| No publishing to claude.ai | `--no-publish` on every command |
| Isolated environments, clean only own temp | Results under the gitignored `results/`; `--keep-temp` only when inspecting, removed after |
| Document a blocked run and propose an alternative | If `claude plugin eval` cannot run under these flags (e.g. Vertex credential loading, a disabled model id — both seen on 2026-10-28), the run fails with an `error` field and `summarize.mjs` surfaces it; the alternative is the Haiku arm (cheaper, same structure) or a dry run (`DRY=1 ./verification/evals/run-evals.sh …`) to confirm the command without spending |

## 6. Residual risks and limits

- **The proxy, not the product.** A pass means the plan follows the method; it does not prove the shipped apps are good. That is why the human visual review runs in parallel.
- **No seed.** Exact reproduction is impossible; only the distribution reproduces. Small deltas are noise.
- **Judge is a model.** Haiku as judge is cheap and was adequate on the smoke cases, but a borderline verdict should be spot-checked, and a second judge can re-score the same answers.
- **Environment flakiness is real** (credentials, model availability). Treat `error` fields as environment, not answer, failures.
- **Leakage is unverified until the leak check runs.** Do not run the scored pilot before confirming the sandbox exposes no graders or prior results.
