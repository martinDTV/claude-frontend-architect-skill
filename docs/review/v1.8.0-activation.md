# Activation — what the model sees, what the pilot showed, what to change (1.8 increment 1b)

Written 2026-11-13 from the official docs (skills, sub-agents, plugin-evals pages of code.claude.com) and the
pilot traces in `plugins/frontend-architect/evals/results/pilot-2026111*` (local). No description was changed here:
a wording change ships only with a before/after on the eight pilot cases (Sonnet, one run per arm — exploratory).

## What the model sees before deciding
- A **listing of name + description** for every available skill; the SKILL.md body loads only on invocation.
  `description` (+ `when_to_use`) is cut at **1,536 characters** in that listing. Ours: `frontend-architect` 948,
  `creative-frontend` 720 characters — under the cap.
- The listing has a **budget of 1 % of the context window**. When it overflows, descriptions are **dropped,
  least-invoked skills first** (names stay). In the eval sandbox the plugin's two skills sit next to 17 built-in
  ones (19 total) with no invocation history on either side. With a 200k-token window the budget is ≈ 2,000 tokens;
  nineteen descriptions can exceed it. Which ones were dropped is not visible in the trace. **Hypothesis**, not a
  measurement: Haiku's 0/8 and Sonnet's 2/2 may partly be a budget effect — a smaller window drops more. The docs
  document no model dependence of triggering; they do say to pin `--model` so a rollout is not read as a regression.
- Official guidance for descriptions: "what the skill does and when to use it", **"put the key use case first"**,
  include the keywords users naturally say; make it more specific if it triggers too often. Subagents: "include
  phrases like 'use proactively'" (ours does); keep descriptions short (they cost context).
- `disable-model-invocation` defaults to `false` and `user-invocable` to `true` — nothing in the plugin prevents
  model invocation (checked by test).

## What the pilot showed
| Run | Model | Activation (Skill / subagent) |
|---|---|---|
| 96 ×3 single runs | haiku | 1 Skill, 1 subagent, 1 none |
| 96 ×2 single runs | sonnet | 2 subagent |
| 8 cases, one run | haiku | 0 / 0 of 8 — with every prompt containing the literal trigger phrases ("Audit … Nuxt 4 … what to fix first") |
| 8 cases, one run | sonnet | 0 / 1 of 8 (arch, via `frontend-reviewer`) — same prompts; the "before" of the wording experiment |

So the prompts are not the problem: they match the descriptions word for word. The decision is the model's, and it is
unstable run to run for both models (Haiku 2/11, Sonnet 3/10 across every run so far). When it activates, it does the right thing (runs the auditors, applies the doctrine).

## What to change (proposal, to be evaluated before/after)
1. **Shorter descriptions, key use case first.** A shorter listing survives the budget more often and the first
   sentence carries the trigger. Proposed `frontend-architect` (≈ 520 chars vs 948):
   > Use when the user audits, reviews, structures or refactors a Nuxt/Vue or Next.js/React frontend, asks "what should we fix first", or asks whether it needs a store, Axios, a monorepo, microfrontends or a migration. Architecture stage, module boundaries, rendering strategy, where state lives (Pinia, Pinia Colada, useState, Zustand, TanStack Query), the API layer, auth and tenancy, forms, tables, i18n, errors, accessibility, performance, testing, deployment, legacy and monorepos — with read-only audit scripts that cite path:line.
   Proposed `frontend-reviewer` first sentence unchanged ("Use proactively when the user asks for an audit…"), body
   trimmed to the script list and the three evidence tiers (≈ 450 chars vs 763).
2. **Measure, do not assume.** Before: the eight cases on Sonnet with the current descriptions — **done** (`pilot-20261113-035705`,
   1/8). After: the same with the proposed ones (≈ 1.2 USD, separate authorization). Report activation per case and arm; keep the one with more activations only if the
   diagnoses do not get worse (judge pass counts). One run per arm: a direction, not a proof.
3. **Keep the indicator honest.** `skill-activation` + `subagent-activation` stay with-only indicators (not scored);
   `arm: both` would make activation part of the score, which is not what the cases measure.

## E0A checks added (`verification/tools/skill-activation-surface.test.mjs`)
Descriptions under the 1,536 cap and under the project's own 1,000-character ceiling; the first sentence of each
skill description names its key use case and a trigger the pilot prompts use; the reviewer says "use proactively";
no `disable-model-invocation: true`; the two skill descriptions do not overlap on the same trigger words in their
first sentence (so the model is not asked to choose between twins).
