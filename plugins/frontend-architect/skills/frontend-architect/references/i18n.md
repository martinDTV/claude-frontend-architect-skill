## Decide the scope

| Situation | Approach |
|---|---|
| One language today, maybe more later | Still use the i18n library's `t()` and `Intl` formatting from day one; retrofitting keys into 80k lines is the expensive part |
| Several languages, same market | Locale in a cookie or user profile, no URL prefix needed for private apps |
| Public pages with SEO in several languages | Locale in the URL (prefix or domain) with `hreflang` and canonical links |
| Multi-tenant SaaS | Tenant default locale and time zone from tenant settings; user override; never from `navigator` alone |

## Routing strategies and SEO

| Strategy | URL | Use when |
|---|---|---|
| `no_prefix` | `/orders` | Private apps; locale from cookie/profile |
| `prefix_except_default` | `/orders`, `/en/orders` | Public site with a primary market |
| `prefix` | `/es/orders`, `/en/orders` | Every locale equal; simplest for SEO |
| Domains | `example.mx`, `example.com` | Separate markets and brands |

SEO: emit `<link rel="alternate" hreflang>` for every locale plus `x-default`, canonical per locale, translated meta and Open Graph, `lang` on `<html>`. `@nuxtjs/i18n` generates them with `useLocaleHead()`; `next-intl` documents `alternates` in `generateMetadata`.

## Locale detection and SSR

Order of precedence: URL (if strategy uses it) → cookie → user profile (after login) → `Accept-Language` → tenant default → app default. Decide on the server during SSR and send the same locale to the client; detecting on the client only causes a flash and a hydration mismatch. Persist the choice in a cookie (`SameSite=Lax`), not in `localStorage` (not readable during SSR). Never keep the current locale in a module-level variable on the server (`state-vue.md`, SSR leaks).

## Messages: format, plurals, rich text

- Use ICU MessageFormat or the library's equivalent for plurals (`{count, plural, =0 {No results} one {# result} other {# results}}`), selects (gender, status) and ordinals; no `if (count === 1)` in templates.
- Rich text and components inside messages: `vue-i18n` `<i18n-t>` with slots; `next-intl` `t.rich()`; never build HTML by concatenating translated fragments.
- Keys: stable, namespaced by feature (`orders.list.empty`), not the English sentence; a missing key must be visible in development (warn/handler) and fall back to the default locale in production.
- Keep interpolation variables named (`{name}`), not positional.

## Dates, numbers, currencies and time zones

- Format with `Intl.DateTimeFormat`, `Intl.NumberFormat`, `Intl.RelativeTimeFormat` (or the library's `d()`/`n()` wrappers) with the active locale; never hand-format.
- Store instants in UTC (ISO strings); display in an explicit time zone. For medical scheduling, logistics and ERP apps the zone is a property of the clinic, warehouse or tenant, not of the browser: pass it explicitly to the formatter (`timeZone: tenant.timeZone`). Calendar dates (birthdays, due dates) are zone-less strings and must not be converted.
- Currency with the ISO code and the locale's conventions; multi-currency tables show the code.
- Construct formatters once per locale (they are expensive) and reuse them (`data-tables.md`).
- SSR: the server and the client must use the same locale and zone or hydration mismatches appear; pass both explicitly, do not rely on the server's system zone.

## Loading and organizing messages

- One file per locale per feature (`features/orders/locales/es.json`), merged lazily; `@nuxtjs/i18n` `lazy: true` with `langDir`, `next-intl` per-request message loading with namespaces. Do not ship every locale's full catalog in the entry bundle.
- Shared vocabulary (actions, states, validation) in a `common` namespace; features reference it rather than duplicating "Save".
- Validation messages: Zod/Valibot locale maps for format rules, product messages from the catalog (`forms.md`).

## RTL and visual internationalization

- Use CSS logical properties (`margin-inline-start`, `padding-block`, `inset-inline`) and `dir` on `<html>`; Tailwind 4 supports logical utilities (`ms-`, `pe-`), check the project's version.
- Icons with direction (arrows, chevrons) flip; media controls do not.
- Text expansion: German and Spanish run 20 to 35% longer than English, Finnish longer; no fixed-width buttons or truncated labels in navigation. Layout rules in the creative skill's `layout-and-responsive.md`.
- Line wrapping and hyphenation differ by language; test the longest locale, not only English.
- Pseudo-localization in development (accented, 30% longer strings) catches these before translators do.

## Vue / Nuxt specifics

- `@nuxtjs/i18n`: configure `locales` with `language` codes, `defaultLocale`, `strategy`, `detectBrowserLanguage` (cookie-based), `lazy` + `langDir`; use `useI18n()`, `useLocalePath()`, `useSwitchLocalePath()`, `<NuxtLinkLocale>`; `useLocaleHead` for SEO tags. Verify option names for the installed 10.x.
- `vue-i18n` 11 in Composition API mode (`legacy: false`), `useI18n({ useScope: 'global' })`; typed messages via a schema type for `createI18n` when the catalog is large.
- Pinia stores and composables receive `t` from `useI18n()` inside setup; services do not translate (they return codes).
- Dates: `$d`/`d()` with named formats per locale, time zone passed explicitly.

## React / Next.js specifics

- `next-intl` 4: `i18n/routing.ts` with locales and prefix strategy, `proxy.ts` (Next 16) or `middleware.ts` (Next 15) running the routing helper, `[locale]` segment with `setRequestLocale` for static rendering, `getTranslations` in Server Components and `useTranslations` in Client Components, `NextIntlClientProvider` with only the namespaces a client tree needs.
- Formatting through `useFormatter`/`getFormatter` with the request's time zone; set `timeZone` in the request config explicitly.
- Keep messages out of Client Component bundles unless used there; server-first translation reduces JavaScript.

## Content that comes from the backend

| Kind of text | Who translates | How |
|---|---|---|
| UI chrome (labels, buttons, validation) | Frontend catalog | `t('orders.actions.approve')` |
| Enumerations (statuses, roles, categories) | Frontend catalog keyed by the code the API returns | ``t(`orders.status.${status}`)`` with a fallback for unknown codes; the API returns `approved`, never "Aprobado" |
| Error messages | Backend returns a stable `code` (+ optional default message); the frontend translates the code | `errors.email_taken`; unknown codes show the server's default message (`error-handling.md`) |
| Entity content (product names, clinic descriptions) | Content owners, stored per locale in the backend | The API accepts `Accept-Language` or a `locale` param and returns the localized field, or all localizations for editors |
| User-generated content | Nobody | Shown as entered, with the author's locale/direction when known |
| Documents (PDF invoices, emails) | Backend templates with the recipient's locale and time zone | Pass the user's locale explicitly; do not derive it from the server |

## Multi-tenant defaults

Each tenant has a default locale, time zone, currency, number/date formats and sometimes a first day of the week; users may override locale and zone within the tenant's allowed set. Resolve: user preference → tenant default → app default, once per request/session, and expose it through one composable/hook (`useLocaleContext()`), never scattered `navigator.language` reads. Cache keys for localized data include the locale; switching locale invalidates them (`realtime-and-sync.md`).

## Translation workflow

- Extraction of keys in CI (the library's or a generic extractor) and a check that every locale has every key (or an explicit allowlist of pending keys).
- Translators work in a TMS or in JSON/YAML files with context comments; developers never edit translated files except the default locale.
- Release: missing translations fall back, logged once per key, not per render.
- Legal and medical texts need review flags; do not machine-translate consent screens silently.

## Testing

- Unit: pluralization and selects for edge counts (0, 1, 2, 5, 21 in languages with complex rules), formatters with explicit zones across DST boundaries.
- Component: render in two locales; assert no hard-coded strings (a test locale that returns the key makes them obvious).
- Key coverage: a test that diffs key sets across locales.
- E2E: one journey in the longest locale and one in an RTL locale when supported; visual regression for navigation and forms in both.

## Anti-patterns

- Concatenating translated fragments (`t('hello') + ' ' + name`); grammar differs by language.
- Translating only in the backend: error codes should travel, not sentences, or both sides end up translating.
- Locale or time zone stored in a module-level singleton on the server (cross-request leak).
- Formatting dates in the server's zone and in the browser's zone on hydration.
- `toLocaleString()` without a locale argument: output depends on the machine.
- Hard-coded widths that fit English only.

## Checklist

- [ ] Strategy chosen (no prefix for private apps, prefix or domains for public SEO) with `hreflang` and canonical when public
- [ ] Locale resolved on the server (URL → cookie → profile → `Accept-Language` → tenant → default) and sent to the client; no module-level locale state
- [ ] ICU plurals/selects; rich text through the library, never concatenation; named variables
- [ ] `Intl` formatters with explicit locale and time zone; UTC instants, zone-less calendar dates; formatters reused
- [ ] Messages split per feature and lazy-loaded; `common` namespace for shared vocabulary
- [ ] Enumerations and error codes translated by the frontend from stable codes
- [ ] Logical CSS properties, `dir` on `<html>`, no fixed widths; pseudo-localization checked
- [ ] Key-coverage test across locales; plural edge cases tested; one E2E journey in the longest locale
